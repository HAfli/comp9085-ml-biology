# The model visualisation architecture

The rule this module is built on:

> **A figure shows what a fitted model actually did, or it says in words what
> it is showing instead.**

No figure on this site is a drawing of what a model might look like. Every one
is produced from an object that was fitted, in the browser, on the data named
in its banner. If a student reads a number off the figure and recomputes it in
the lab, the two agree.

---

## The layers

```
js/data/wdbc.js, sequences.js, ...   real (or clearly labelled simulated) data
          |
js/ml.js                             the learners: CART, k-NN, naive Bayes,
          |                          logistic regression, PCA, k-means, DBSCAN,
          |                          agglomerative clustering, random forest
js/visualisations/_model.js          draws FITTED objects, nothing else
          |
js/visualisations/_chart.js          axes, frames, tooltips, legends, responsive
          |
js/visualisations/<figure>.js        one file per figure: state, controls, text
          |
js/week-page.js  VIZ_SPECS           the controls, the readout, the alt label
```

A figure file owns its state and its controls. It does not own a drawing
routine for a model type: that lives in `_model.js`, so the tree drawn by the
Week 2 builder, the tree drawn by the deployment interface and (later) the
trees drawn inside a random forest are the same code reading different fitted
objects.

---

## What `_model.js` provides

| Function | What it does |
|---|---|
| `Model.tree.hierarchy(root)` | Wraps a fitted `js/ml.js` tree for d3 |
| `Model.tree.draw(stage, root, depth, opts)` | Renders it. `opts.highlight` marks a decision path, `opts.selected` marks an inspected node, `opts.onSelect` makes nodes clickable and keyboard-operable |
| `Model.tree.trace(root, values, indexOf)` | Walks one case through the tree and returns the path and the test at each step |
| `Model.tree.inspectorHtml(node, opts)` | The node inspector table. Reports only fields the node actually carries |
| `Model.pathPanel(trace, opts)` | The decision path as an ordered list, with the causality disclaimer |
| `Model.pretty(name)` | Feature names for display |

Everything renders into the standard figure shell from `C.vizShell`, so each
figure keeps its reset button, its readout, its explanation and its text
alternative without special cases.

## Extending it to the other weeks

The contract for each model type is the same: take the fitted object, draw what
is in it, and let the text alternative carry the same information.

| Week | Model | What the figure must show |
|---|---|---|
| 5 | Naive Bayes | The per-class log-likelihood terms the model summed, and the posterior it produced |
| 7 | PCA | The projected coordinates the fitted model returned, and the explained variance it reports |
| 8 | k-NN | The query point, the k neighbours the model actually retrieved, and the vote |
| 9 | k-means, DBSCAN, hierarchical | The cluster assignments the fitted model returned; the real dendrogram from the real linkage |
| 10 | Random forest | Several trees drawn with `Model.tree.draw`, then the aggregation |
| 11 | Boosting | The weak learners in sequence and the residual each one corrected |

**Do not** add a helper that draws a plausible-looking picture the model did not
produce. If a model cannot be drawn honestly at the scale in question — a
hundred-tree forest, a transformer — say what is being visualised instead. The
foundation-model figures in Weeks 7 and 11 do exactly that: they show the
pipeline, and the embedding explorer plots real projected coordinates, never an
imagined internal state.

## Provenance

Every figure carries a banner generated from a flag in its data file, not from
prose in the figure:

| Banner | Meaning |
|---|---|
| **REAL** | Measured data or measured model output |
| **SIMULATED / ILLUSTRATIVE** | Generated by a script shipped in `data/scripts/`, which the banner names |
| **LIVE** | Computed in the browser as you move the controls |

The Week 2 deployment demonstration carries an additional statement, on the
interface itself and in its text alternative:

> Educational deployment demonstration using the teaching model. Not a clinical
> diagnostic system.

---

## Two rules about language

1. It is a **decision path**, not "the reasoning", not "why the AI thinks
   this". The path is the sequence of learned splits an input followed. It does
   not establish causality and it is not a clinical explanation. This wording is
   used identically in the deck, on the site and in the lab.
2. A figure's **text alternative contains the information**, not a description
   of the picture. It is what a screen-reader user, a printed page and a
   student who would rather read numbers all get, and it is tested: every
   figure must populate it, or `data/scripts/test_site.py` fails.

---

## Testing a new figure

```bash
python3 -m http.server 8899 &
python3 data/scripts/test_site.py          # renders, links, labels, alt text
python3 data/scripts/test_interactions.py  # sweeps every control on every figure
```

`test_interactions.py` fails a figure whose output does not change when its
controls are swept, which catches the specific failure this architecture is
meant to prevent: a figure that draws correctly and ignores the model.
